## Update — lighter theme + Greek-inspired type system

Reworked the visual language per client direction: "blue and white, but lighter, chill vibes"
plus real Greek-style calligraphy instead of the plain sans-serif.

- **Palette softened** (`tailwind.config.ts`): the old strong navy (#0d3b6f/#082746) is now a
  "harbor blue" (`cobalt` = #2f5578 / light #6d93b4 / dark #1c3850) — still clearly "the blue,"
  much less heavy. Contrast-checked against white text (7.8:1 DEFAULT, 12:1 dark — both pass
  WCAG AAA). Added `mist` (#eef3f5, pale blue-grey) for alternating section backgrounds instead
  of flat white/cobalt-tint, and `sand` (#faf8f4, warm off-white) as the new body background —
  the whole site no longer sits on stark white.
- **Typography** (`app/layout.tsx`): swapped Space Grotesk for **Cinzel** (a serif carved from
  actual Roman/Greek inscriptional lettering) as the display/heading font, and added
  **Cormorant Garamond italic** as a script accent font (`font-script`) for small taglines —
  e.g. "Est. on Hindley Street" over the hero, "Yamas!" over the final CTA. Body copy stays on
  Inter for readability.
- **New decorative motif**: `public/images/marble-scene.svg` — an original, hand-built SVG
  (soft blue-grey gradient, one large "orb," abstracted column line-art, a meander trim strip)
  used via the new `.scene-bg` utility class behind the hero and the two navy call-to-action
  sections on the homepage. This is intentionally *not* a copy of any reference/mood-board
  image — the client's references included another studio's Canva stock asset and two other
  restaurants' branding (PHEAS, NOMA), which aren't ours to reuse on a paying client's site, so
  the mood was rebuilt from scratch as original artwork instead.
- Logo files were **not** recolored — they stay the bold "signature" navy from the brand mark,
  which now reads as an intentional deeper accent against the lighter site chrome.

Because the whole codebase already used semantic classes (`font-display`, `bg-cobalt`,
`text-cobalt`) rather than one-off hex values, this change cascades through every page
automatically — About/Location/Contact/Order all pick up the new palette and type without
being touched individually. Homepage got extra hand-styling (script taglines, the marble scene
on hero + two CTA blocks) since it's the highest-visibility page.

**Next up, by design:** the actual `/menu` page layout and the `/order` builder UI haven't been
redesigned yet — they're functionally intact but visually still plain. That's the deliberately
separate next step (menu content/pricing was already finished in the previous pass; now it's a
pure visual pass on the same new design system).

## Update — menu rebuilt as an option-driven system + full copy rewrite

### New menu model (`lib/menu.ts`)
The flat category/item list in `lib/content.ts` is **superseded** (left in place,
clearly marked, nothing imports it — it preserves the client's original confirmed
price list for cross-checking). Both `/menu` and `/order` now read `lib/menu.ts`.

Structure is option-driven, not one-line-per-permutation. A customer picks a
product, then meat / size / extras:

- **Meat** is a multi-select: tap one for a single meat, or two or three for a
  **Mix**. Lamb carries a **+$2** surcharge, applied once if lamb is in the
  selection. Groups: Yiros, Yiros Pack, AB Pack, Meat Pack, Platters (dine-in
  only), Sides & Sauce, Coffee, Drinks.
- **Extras rules live in the data** (`allowedExtras` per product), so the
  restrictions can't drift out of sync with the UI:
  - Yiros → cooked onion, chips, cheese, extra meat (all four)
  - Yiros Pack → **no chips**
  - AB Pack → **no chips** (it already comes on chips)
  - Meat Pack → **no extra meat**
  - Platters → cooked onion, cheese
- **Drinks are grouped, not listed flat**: five products (Soft Drink, Can, Water,
  Juice/Milk/Iced Coffee, Sports & Energy) each with a flavour sub-select, plus
  Greek Coffee on its own. This replaces the seven separate drink categories.

### Order builder (`components/OrderFlow.tsx`, `components/ProductCustomiser.tsx`)
The "Add" button problem is fixed. Tapping a product now opens a customiser sheet
(slides up on mobile, fades in on desktop) with meat/size/variant/extras chips, a

"✓ Added to your order" for ~1.6s, and the cart badge bumps. The summary panel

total. All animations respect `prefers-reduced-motion`.
New CSS in `globals.css`: `.chip-option`, `.qty-btn`, `.customiser-sheet`,

## Update — sauce allowances + design theme rebuilt

### Sauce rules (`freeSauces` per product)
Two sauces included on every food item, **three on an AB Pack**, then
**$0.50 per additional sauce**. The allowance lives on the product
(`freeSauces`), and `sauceCost(selected, free)` does the maths. The
customiser shows a sauce picker: chips past the allowance pick up a visible
"+$0.50" badge and a running line explains the overage. The old standalone
"Extra Sauce" product was removed — sauce choice is now part of each item,
so a separate line item would have been a second, contradictory way to buy
the same thing. (Garlic Sauce *tubs* remain a product; that's a different
thing.)

### Design: the still-life is now a theme, not a pasted picture
**What was wrong.** `.scene-bg` set the whole reference composition as
`background-image: cover` behind the hero, the "Why" band *and* the final
CTA — the same photograph appearing three times down one page. Worse,
`column-left.png` / `column-right.png` were **crops of that same photo**,
carrying their own marble wall and drop shadow, so they could only ever be
pasted beside content, never actually frame it.

**What replaced it.**
- **`components/ornament/Column.tsx`** — a fluted Doric column drawn as
  vector (capital, abacus, echinus, necking rings, flutes, torus, plinth).
  It uses `currentColor` and gradient opacity, so it tints to any section
  and composites at any opacity with no baked-in background.
- **`components/ornament/Rosette.tsx`** — the carved medallion redrawn as
  vector, for 6–7% background watermarks.
- **`components/ornament/TempleFrame.tsx`** — **the pillars now hold
  something.** Two columns carry a lintel with content standing between
  them, on a stylobate. Used for the hero (columns carrying the name), the
  homepage About image and the About-page storefront. Columns hide below
  `sm` where they'd only steal width from the content they frame.
- **`.scene-atmosphere`** — the photo survives only as a 9% wash with a
  radial mask so it fades at the edges (16% + `soft-light` on cobalt
  sections). Depth, not decoration.
- `.marble-wash` is retired from the pages; `.plinth` and `.carved-panel`
  are kept — those were already doing real work.

### Colour distribution
The palette was blue-and-white only, so every accent had to be the same
cobalt — which is why it read flat and repetitive. Added **`brass`**
(`#a8873f`), taken from the Spartan helmets on the actual shopfront sign,
as a third colour: section eyebrows (`.eyebrow-brass`), header rules
(`.meander-divider-brass`, now used on every page header), review stars,
and the "Yamas!" line. Section rhythm is now deliberate and alternating:
`sand → mist → sand → cobalt-dark → mist → sand → mist → cobalt`, instead
of near-identical marble bands throughout.

### Greek humour — `shopStats` + `components/StatsBand.tsx`
Replaces the five near-identical "Why Yianni's" bullets that were padding
the deep-blue band. Four deadpan figures in a colonnade (vector columns as
the dividers): **3** meats total ("There is no fourth. People ask."),
**0** recipe changes ("It was right the first time."), **40-ish** years on

garlic restraint ("You will know. Tomorrow, your colleagues will know.").
The "Why it's lasted" points survive as a quieter 3-up list on the pale
band, so the page isn't repeating the same card treatment.

## Rewards program — AGREED SPEC, NOT YET BUILT

Worked out with the client; no code written for this yet. Recorded here so the
reasoning isn't lost.

### Program
- **Earn:** 1 stamp per order of **$29 or more**. ($29 chosen so a chicken yiros
  $20 + small chips $9 lands exactly on the threshold.)
- **Ladder:** 5 stamps → Greek coffee · 10 → small chips · 15 → chicken or pork yiros
- **Expiry:** 6 months. **Open question: from joining, or from the last stamp
  earned?** Recommended from-last-stamp — a fortnightly regular can't finish a
  15-stamp ladder in a fixed 6 months and would lose ~11 stamps, which reads as
  a trick. From-last-stamp gives the same liability protection without punishing
  active customers.
- **Guardrails:** lamb excluded from the free yiros; one stamp per email per day.

### How a stamp is earned (no POS)
The shop has **no POS — a manual till, cash and change only**, so the system
cannot see a sale and a human must vouch for it. Agreed mechanism: a **rotating
code given verbally at payment, never displayed on the counter** (a displayed
code can be read by anyone walking in, or texted to friends). The customer
enters their email + code on the rewards page. Same mechanism covers walk-ins
and online pickup — and it fixes the online fake-order problem, since no
collection means no code. Fallback if leakage becomes real: one-time-use printed
slips dropped in the bag.

### Unit economics (derived with the client)
Meat per regular yiros measured by volume, no scales: a 215mL Genfac cup packed
full plus a partial cup ≈ **250g cooked**. (An initial 60% packing-density
assumption gave ~167g and was wrong — moist compressed meat packs ~90%. The
client's own estimate of 250–300g was correct.)

Raw meat: chicken $9/kg, pork $10/kg, lamb $16/kg. At an assumed **35% raw-to-served
loss** (⚠️ still unverified — see below) and ~$2 for pita/salad/sauce/packaging:

| | Food cost per regular yiros |
|---|---|
| Chicken | ~$5.45 |
| Pork | ~$5.85 |
| Lamb | ~$8.15 |

Chips: $52 per box of 6 × 2kg bags. One bag = 1 family + 1 large; 1 large = 1.5
smalls. So ~4.5 "smalls" per bag → **small chips ~$2.45**, family ~$3.35.

**Program cost: ~$8.40 given away across ~$435 of spend ≈ 1.9% of revenue.**

### ⚠️ Two margin findings that matter more than this program
1. **Lamb may be underpriced.** At 250g, a lamb yiros costs ~$8.15 in food
   against $22 — ~37% food cost before charcoal, power or wages. Lamb costs
   $2.70 more than chicken in meat alone but only carries a **$2** surcharge.
2. **Chips are the best-margin item** (family chips ~17% food cost, roughly
   double a yiros). Converting one customer in ten to add chips likely outearns
   the entire rewards program.

### Still unverified
**Cook loss is an assumption (35%), not measured.** It's the largest remaining
variable. Settle it without scales: **raw kilos loaded on a spit ÷ yiros served
off it** = real raw grams per yiros, trim and shrink included. That would also
answer whether the lamb surcharge is right.

### Build implications when this goes ahead
Needs a **database** and an **email service** (Resend or similar) — both ongoing
costs. Holding customer email + stamp history means the **privacy policy must be
updated**, and under the Spam Act every email needs a working unsubscribe link.
Expiry terms must be disclosed at signup and restated in emails (ACL).

## Update — /kitchen and /admin staff areas

Two password-protected pages, plus the plumbing behind them. **No new npm
packages**: Supabase is reached over its REST API with `fetch`, and sessions
are signed with Node's built-in `crypto`. `npm install` adds nothing new.

### What was built
| Path | Purpose |
|---|---|
| `/staff` | Login screen (shared password) |
| `/kitchen` | Live order board — accept, reject, set wait time, mark collected |
| `/admin` | Upload/replace/remove the Parea Mas team photo |
| `/api/orders/digest` | Cron job: emails the day's orders, then deletes them |

### Setup required before any of it works
1. **Supabase** — create a project, then:
   - SQL Editor → paste and run `supabase-schema.sql`
   - Storage → New bucket named **`media`**, set **Public**
   - Project Settings → API → copy the URL and the **service_role** key
2. **Resend** (resend.com) — API key, and verify a sending domain
3. **Set the env vars** in `.env.example` (copy into `.env.local` locally, and
   into the host's dashboard for production — `.env.local` does not deploy)
4. Generate the two secrets with `openssl rand -hex 32`

### Security notes
- `SUPABASE_SERVICE_ROLE_KEY` bypasses all row-level security. It is used
  **server-side only**; no client component imports `lib/supabase.ts`
  (verified). Never expose it to the browser.
- RLS is **enabled with no permissive policy** on both tables, so a leaked
  anon key still reads nothing.
- `middleware.ts` only checks a cookie *exists* — Edge runtime has no
  `node:crypto`. The real signature check is `lib/requireStaff.ts`, called by
  every protected page and API route. Don't rely on middleware alone.
- Login failures sleep 600ms and return a vague message, to slow guessing.
- The `next` redirect param is restricted to internal paths (no open redirect).
- `/api/orders/digest` is guarded by `CRON_SECRET` because it **deletes** data.

### Design decisions worth knowing
- **Shared password, not user accounts.** A kitchen tablet and the owner's
  phone are the only devices; per-user records would be overhead nobody
  maintains. Changing `STAFF_PASSWORD` signs everyone out — the intended
  "someone left" lever.
- **Polling every 15s, not websockets.** Simpler, survives flaky wifi, and
  15s is fine for a kitchen. New orders trigger a WebAudio beep (no audio
  file to ship); staff can mute it.
- **Optimistic UI** on accept/reject — the kitchen shouldn't wait on a round
  trip mid-service. Reverts and reloads if the save fails.
- **Digest emails before deleting.** If the email fails, orders stay put and
  the next run retries. Losing a day's records to a transient email error
  would be unrecoverable.
- **One photo, fixed storage path.** Each upload overwrites the last, so
  there is nothing to clean up and storage never grows.
- The Parea page prefers the uploaded photo and falls back to
  `lib/parea.ts`, so it still works with no database configured.

### Cron
`vercel.json` runs the digest **Sundays at 10:30 UTC** — 8:00pm ACST / 9:00pm
ACDT in Adelaide. ⚠️ The schedule is fixed UTC, so the local time shifts by an
hour across daylight saving; harmless for a weekly summary.

### Orders are kept, not deleted
Changed from daily-delete to **weekly digest + archive**. `archived_at` marks
an order as already reported; nothing is ever destroyed. At ~1KB a row, even
100 orders a day for five years is under 200MB — inside Supabase's free tier,
so retention costs nothing.

This also means the data is there for real questions later: which days are
actually quietest, what the average order is, whether a promotion moved
anything. Those were being guessed at.

The digest selects `archived_at is null`, so a missed week is picked up by the
next run rather than lost. Archiving happens only after the email is away.

### Not verified
No `npm run build` was possible (no network in the build container). Syntax,
import paths and named exports were checked programmatically. **Run a build
and test the login flow before deploying.**

  the "Send Order" button throws a fountain of sparks** (`igniteEmbers` in
  `lib/embers.ts`; the form holds for ~1.3s so the customer sees it before
